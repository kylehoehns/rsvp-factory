# Ids can't be guessed

Members, groups and events have UUIDv7 primary keys generated by Postgres, not sequential numbers. With sequential ids anyone could walk `/groups/1`, `/groups/2`, … and reach every group, every event and every venue, even though there is no endpoint that lists groups; the ids also told anyone how many groups, events and members existed. A random id makes a link the only way in, which is the visibility the spec intends: anyone with the link may look.

We changed the keys themselves rather than adding a separate public id beside a numeric key. Two ids per row means every module boundary has to know which one it holds, a common source of leaks and bugs, and with no production data the switch was as cheap as it will ever be. We chose UUIDv7 over UUIDv4: its leading timestamp keeps the primary-key indexes compact, at the cost of revealing roughly when a row was created, which is not a secret for public events.

## Consequences

- Every column that holds a member, group or event id in any module is a UUID. Modules still refer to each other by id only, with no foreign keys across modules.
- The API carries these ids as UUID strings. A path id that isn't a UUID is answered like one that names nothing (`<what>-not-found`, 404), so probing learns nothing.
- Seeded demo members have fixed UUIDs.
- RSVPs keep their own key: it never leaves the database.
